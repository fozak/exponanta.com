Dynamic Resource Loading with loader.js

One script tag in your HTML head. Everything else — CSS layers, fonts, JS dependencies, versioning — managed in a single file you control.

E
Exponanta
May 29, 2026 · 7 min read

The Problem with Scattered Tags

Most HTML pages accumulate resource tags over time. A typical blog post head ends up looking like this:

<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@tabler/core@latest/...">
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@tabler/icons-webfont@latest/...">
<link rel="stylesheet" href="/assets/added.css">
<script src="https://cdn.jsdelivr.net/npm/@tabler/core@latest/dist/js/tabler.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>
<script src="/assets/js/auth.js"></script>

Three problems compound each other. First, @latest means any CDN update silently changes what your page loads — a vendor CSS change breaks your layout with no warning and no connection to the cause. Second, the same tags are copied across every page, so updating a version means finding and editing every HTML file. Third, there is no guaranteed load order — CSS layers must load in sequence or overrides apply to nothing.

The membership process on a platform like Exponanta illustrates the same pattern at a higher level. A new member joining a business club goes through guest visits, an interview, and formal onboarding — each step in a defined sequence. Skip a step or reverse the order and the process breaks down. Resource loading works the same way: CSS layers have a strict sequence, and violating it produces silent failures.

CSS Layers Are a Sequence Contract

Before solving the loading problem it helps to understand why order matters. A well-structured frontend has three CSS layers:

Layer 1 — tabler.min.css       vendor base, never touch
Layer 2 — tabler-brand.css     stable brand overrides only
Layer 3 — added.css            active work, page-specific rules

Layer 2 overrides Layer 1. Layer 3 overrides both. If Layer 3 loads before Layer 2, the brand tokens it depends on do not exist yet. The override applies to nothing. The page renders incorrectly with no error message — the browser does not tell you the load order was wrong.

This is the core problem loader.js solves: it owns the sequence and enforces it programmatically, so no individual page can accidentally get it wrong.

The loader.js Pattern

Replace every <link> and <script> tag in your HTML with a single script tag:

<head>
  <script src="https://cdn.jsdelivr.net/gh/fozak/common@v1.0.0/exponanta.com/loader.js"></script>
</head>

loader.js carries the full asset list and injects everything in the correct order. Head resources — CSS that must load before first paint — are injected immediately. Body resources — JS and non-critical assets — are injected after the DOM is ready.

const ASSETS = {
  head: {
    favicon: '/assets/favicon.svg',
    preconnect: ['https://rsms.me'],
    css: [
      'https://rsms.me/inter/inter.css',
      'https://cdn.jsdelivr.net/npm/@tabler/core@1.4.0/dist/css/tabler.min.css',
      'https://cdn.jsdelivr.net/npm/@tabler/icons-webfont@latest/dist/tabler-icons.min.css',
      'https://cdn.jsdelivr.net/npm/@tabler/core@1.4.0/dist/css/tabler-marketing.min.css',
      '/assets/added.css'
    ]
  },
  body: {
    js: [
      'https://cdn.jsdelivr.net/npm/@tabler/core@1.4.0/dist/js/tabler.min.js',
      'https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js',
      '/assets/js/auth.js'
    ]
  }
}

Two-Phase Loading

The loader splits into two phases that map directly to the browser rendering pipeline.

Phase 1 — head resources run immediately when the script executes. CSS <link> tags are injected in sequence. The browser fetches all CSS files in parallel but applies them in DOM order, which preserves the layer contract. The favicon and preconnect hints are also injected here so the browser starts the font connection as early as possible.

Phase 2 — body resources run after DOMContentLoaded. JS files are injected in sequence — each waits for the previous to finish before the next starts. This guarantees that Tabler JS is ready before Alpine.js initializes, and Alpine is ready before your application code runs.

loadHead()
document.addEventListener('DOMContentLoaded', loadBody)

Versioning and the Tag Contract

loader.js itself is versioned via a GitHub tag. The CDN URL contains the tag explicitly:

cdn.jsdelivr.net/gh/fozak/common@v1.0.0/exponanta.com/loader.js

A tagged URL is frozen forever. jsDelivr sends Cache-Control: immutable for tagged files, meaning returning visitors load loader.js from the browser cache instantly — zero network request. The same applies to every asset URL that includes a pinned version number.

When you need to update an asset — say Tabler upgrades from 1.4.0 to 1.5.0 — you edit loader.js once, commit, and create a new tag. Every page on every site that references the new tag gets the update simultaneously. No page-by-page editing.

Multi-Site Benefit

The pattern scales naturally across multiple sites. Each site has its own loader.js in the shared repo:

common/
  exponanta.com/loader.js
  cfeglobal.org/loader.js
  bostonelitecontractors.com/loader.js

Layer 1 — the vendor Tabler CSS — is the same URL across all three loaders. A user who visits exponanta.com first has that file cached. When they visit cfeglobal.org, Tabler loads from cache instantly. Shared vendor assets across domains cost one network request total, not one per site.

What This Looks Like in Practice

A complete blog post HTML file is now around 40 lines. The head contains only meta tags, structured data, and the single loader script. No asset management, no version numbers, no load order decisions. Those concerns live in one place — loader.js — and are settled once.

The same principle applies to joining a business network. A well-run club does not ask each new member to figure out the onboarding sequence themselves. The process is defined once, managed centrally, and every new member follows the same path. loader.js applies the same thinking to frontend assets: define the sequence once, enforce it everywhere, update it in one place.
